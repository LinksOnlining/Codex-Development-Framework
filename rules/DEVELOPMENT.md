# Development

本文件是项目初始化、开发强度、Task Batch 与普通技术决策的单一事实来源。

## 新项目初始化

仅在 `rules/REQUIREMENTS.md` 的需求门禁通过并获得用户明确确认后执行：

1. 在 `D:\AI_Workspace\Projects` 下创建新的同级项目目录，禁止放入或整目录复制 `AI_Project_Template`。
2. 按需读取 `templates/`，为项目生成自己的 `AGENTS.md`、`PROJECT_BRIEF.md`、`PROJECT_STATUS.md`、`DESIGN.md`、`README.md`、`CHANGELOG.md`。
3. 只有项目存在特殊环境、工具、约束或发布流程时才创建 `CODEX.md`。
4. 根据确认后的技术栈创建真正需要的源码、测试、文档、脚本、数据库、资源和配置；不机械套固定目录。
5. 把需求写入 brief，把当前阶段写入短 status，然后进入 Phase 1。

中央库保持不变，项目文档不得反向引用归档内容作为有效规则。

## 开发模式

### FAST

适用于小型 Bug、文案、小 UI、简单配置和低风险局部修改。

流程：定位 → 修改 → 快速验证 → 完成。

### STANDARD

普通功能和中等规模修改的默认模式。

流程：分析 → Task Batch → 实现 → 针对性测试 → 修复 → PASS → 必要文档更新。

### DEEP

适用于架构、数据库 Schema、Migration、核心算法、大规模重构、安全、数据完整性和其他高风险修改。

流程：分析 → 设计 → 分阶段实现 → 针对性验证 → 回归 → 工程审查 → 文档 → Git milestone。

不要把普通任务升级为 DEEP；风险和影响降低后也不要保留不必要的流程。

## Task Batch

把同一目标、同一模块或同一验证链上的相关小修改组成一个合理批次：先一起分析，再批量实现并执行一次有针对性的验证。不要在每个小文件后重复汇报和全量测试。

无关任务、风险等级不同的任务、需要不同用户决策的任务不得强行合并。发现无关问题时记录到合适位置，除非它阻塞当前任务或造成严重安全、数据或运行风险。

## 技术自主权

需求明确后，普通实现细节由 Codex 自主决定。优先成熟、简单、稳定、少依赖、低维护、与现有架构一致且适合当前规模的方案；先复用现有实现、标准库或平台能力。

不为未来可能性提前增加框架、服务、中间件、抽象、微服务或大型依赖。可靠功能必需的输入校验、错误处理、安全措施和可访问性必须保留。

重大产品或架构决策按 `rules/SAFETY.md` 请求用户决定。

## 大阶段门禁

大阶段结束时执行必要测试与回归、工程自检、问题修复、再次验证、必要文档同步和 Git milestone；简要汇报后等待用户确认，再进入下一大阶段。
