# Requirements

本文件是新项目需求门禁与需求变更的单一事实来源。

## 何时触发

当用户要创建新的软件产品、应用、服务、库或仓库时触发。继续已有项目、修复现有代码或维护中央规范不重新执行完整的新项目访谈。

## 新项目硬门禁

用户刚提出项目时不得立即编码、初始化技术栈或创建正式项目结构。先进行需求访谈；只允许做澄清所需的只读检查、研究和聊天内草案。

提问应批量且高信息密度，并根据回答继续追问仍然缺失、冲突、有歧义或会影响产品方向、架构、风险和验收的内容。减少轮次不能以遗漏关键问题为代价。

按项目实际情况确认：

- 目标、目标用户、核心问题与成功条件；
- 交付目标：Complete、MVP、Prototype、Demo 或其他，以及对应完整性要求；
- 核心场景、必须功能、可选功能和非目标；
- 平台、系统版本、发布与更新方式；
- UI / UX、可访问性和文件格式；
- 数据来源、存储、迁移、备份与保留；
- 联网、API、第三方服务、登录、账号和权限；
- 性能、安全、隐私、依赖、成本和运维约束；
- 可观察且可测试的验收标准。

选择 Complete 时，根据用户真实要求在 `Completeness Requirements` 中明确生产或长期可用性，以及全部 Must Have 和 Acceptance Criteria 均为强制项；不要机械复制固定措辞，也不要自行把 Complete 解释成缩减版交付。

持续澄清，直到对整体需求达到约 95% 理解把握：没有尚未解决且会实质改变产品、交付完整性、架构、安全、成本或验收的关键问题。交付目标不明确时必须询问，不得自行把 Complete 降为 MVP、Prototype 或 Demo。

达到门槛后，向用户简洁总结项目目标、Delivery Target、核心功能、非目标、关键约束、技术边界和验收标准，并等待用户明确确认。只有确认后才可创建正式项目和进入 Phase 1。速度、Token 或 Codex 自认为能猜到，都不能跳过该门禁。

## 确认后的要求事实源

把确认结果写入项目根目录的 `PROJECT_BRIEF.md`。后续任务先以该文件为需求事实来源，不从长聊天记录反复推导。

新要求仅是补充且不改变已确认边界时，可直接更新并实施；若与 brief 冲突或显著改变范围、产品行为、架构、风险、成本或验收，先说明冲突并请用户确认，随后更新 brief 再实施。
